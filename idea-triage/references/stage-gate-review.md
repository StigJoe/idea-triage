# 阶段复审与项目状态

在项目阶段结束、条件到期、关键假设被推翻或用户请求时复审。先读当前需求、用户决定、最近结果和条件。重查会改变方向的关键证据。保留最强反方、可能错在哪里、建议继续或转向的依据。范围、权限或目标改变时标出失效部分。复审建议和项目的实际决定分别保存。

## 正式记录工具

用技能安装目录下的 `scripts/triage.py`。以下 `SKILL_DIR` 是该目录，`PROJECT` 是一个想法的资料目录。运行前确认 Python 3.9 或以上及标准库 SQLite。只有明确需要落盘才初始化状态。把 `.idea-triage/` 加入该项目的忽略规则或保存在获准的本地位置。

1. 评估开始时执行 `python3 "$SKILL_DIR/scripts/triage.py" --project "$PROJECT" snapshot requirements.md`，保留返回的 SHA。报告用 verdict 模板并用稳定文件名保存。
2. 运行 `validate <报告>` 和 `tier <报告>`。前者核通用结构，后者另核两轴、条件和证据格式。正式报告的 `networked: yes` 后写一个明确的检索日期，日期须在评估当天或之前。正文的 `## 关键证据` 每行按 `- [等级] 主张 | [来源](https://example.com/source) | 局限` 写，等级选一手资料、静态核验、合成验证或真实实测。将示例地址换成直接网页链接或相对报告的项目文件链接。最后写 `- 改判条件：` 及会改变建议的可观察结果。工具检查格式与本地文件存在性，评估者仍须核对实际取证、每条主张是否获支持和证据等级。缺关键证据时输出暂定结果。
3. 评估留档用 `register <评估ID> <报告> --requirements requirements.md --requirements-sha <此前的SHA>`。正式登记和 `tier` 使用同一证据闸门。同一 ID 和内容重跑只记一次。报告或需求换版本用新 ID。注册只记录建议，不更新当前决定。
4. 使用 `status` 获取项目版本和当前决定。用户明确决定后执行 `decide <评估ID> --expect <当前版本> --date <YYYY-MM-DD> --reason <用户决定依据>`。如有用户明确改判，使用 `--verdict <用户判定>`。过期版本与已改文件会被拒绝，重新读取后再处理。旧文件可用 `register ... --legacy` 登记为历史。
5. `due --as-of <YYYY-MM-DD>` 检查截至该日期的最新用户决定和未解决的到期条件。到期当天需要处理，之后补证不会改变此前日期的到期结果。报告和需求指纹与当前文件核对。条件满足后，保存核验依据并用 `resolve <条件ID> --expect <当前版本> --date <YYYY-MM-DD> --reason <证据>` 更新。决定日期不得早于报告或上一决定，解决日期不得早于对应决定。
6. `backup <新路径>` 保存独立的状态副本，备份报告和需求文件仍需保留其相对位置。恢复前关闭相关写入并核对副本与文件，保留此前数据库。报告与需求可直接读，`status` 可输出状态和历史。

新报告用 `score_profile: track-v1` 选择赛道权重，`tier` 和 `register` 返回赛道版本、三项档位及成本效益。`null` 成本效益表示待验证。`status` 的 `direction` 和 `outlook` 是登记时的分数，成本效益、提档依据与复评对照保存在指纹绑定的报告里，需重算时对原报告运行 `tier`。旧件无评分版本时按旧权重计算。分数隐含判定与评估建议不同时，解释反证或阶段门为何改变了建议。带版本报告的 `tier` 表示对当前步骤的建议，旧报告仍显示原投入分层。确认项目状态用 `decide`。

工具退出 0 表示当前操作通过，1 表示冲突或需复审状态，2 表示输入、文件或运行错误。注册报告后如果需求或报告被改，状态仍可追溯，复审需以新输入形成新记录。多人共享时先验证实际文件系统和备份方案。
