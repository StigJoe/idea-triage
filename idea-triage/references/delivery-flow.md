# 从想法到交付：阶段与证据

复杂评估、跨阶段续跑或需求变更时读。核心是每份文档有不同职责，下一步能引用上一阶段的依据；不是靠文件数量证明工作完成。

## 1. 基线先于深选方案，但不是禁止探索

可以先做低成本事实查找，帮助弄清问题。用户、用途、关键约束仍未定时，不先选具体产品或设计定案架构。已经明确的指令与回答可以直接形成需求基线，无需每写一份文档再请用户批准。

需求说明“什么结果有用”，方案说明“采用什么做法”。例如“手机能随手记录并取回资料”是需求，某款笔记软件是候选；只有用户明确指定为硬约束时才进入需求。

正式评估使用requirements.md或已存在的权威需求。简单想法可以半页；纯登记只有brief；已有需求只建映射/链接，不能复制出两套会漂移的SSOT。

## 2. 每阶段至少解决一个问题

| 阶段 | 应回答 | 达到什么程度才能继续 |
|---|---|---|
| 发现/澄清 | 为谁，在哪个场景，现有做法哪里不够？ | 重大意图有依据；待查事实与用户取舍分开 |
| 定义需求 | 当前包含什么、不做什么、怎样验收？ | 核心需求有编号/优先级/结果；候选方案未冒充硬需求 |
| 复用/调查 | 已有什么，关键假设成立吗？ | 三来源有实际记录或不可用说明，证据对应需求，最大风险清楚 |
| 方案收敛 | 哪条路线最划算，为什么？ | 真实候选的收益、缺口、维护、接口/事实归属与止损可解释 |
| 验证 | 哪个假设一旦失败会推翻方案？ | 先写判据，运行获准的最小验证；结果和限制可追溯 |
| 结论/最小计划 | 做/复用/换方向/不做，投多少？ | 现有 verdict 契约、评分表、提档证据、下一边界齐全；复杂任务有获选路线计划 |
| 实施/验收/复盘 | 承诺结果是否真的发生？ | 在用户授权范围内执行；验真实产物和使用，不只验文档或演示 |

这些阶段可回访，不要求从头重做。早期“有条件行”可以是完整评估结论；真正项目实施仍按权限和主任务要求执行，不能把评估结论当新项目授权。

## 3. 文件按决策分工

- brief：登记、动机和导航，不维护整页重复需求。
- requirements：唯一需求基线，保留R编号与确认依据；它不是把所有实现细节提前写死的规格书。
- research：针对需求与未知取证；按类型选维度，不对自用强做商业市场报告。
- decision：复杂项目的候选对照、获选方案、关键验证与最小实施计划。小项目可并入verdict，不强凑候选和文件。
- verdict：对当前范围的评估和投入，使用机器可读头块。评估历史、用户决定与复审条件通过[状态工具](stage-gate-review.md)维护。
- 验证证据：放在现有validation或research目录；未运行明确未运行，不先造空产物。

只有真实复杂度需要时，才继续拆出独立架构、接入前提、部署、合规或分阶段实施文档。团队产品的文档规模不自动适用于单人脚本。

## 4. 风险优先、投入有边界

借用四类风险视角：价值、可用性、可行性、长期成立条件。它们用于找最薄弱的假设。需要评分时采用赛道口径。

自用的长期成立看维护、成本和机会成本；科研看问题是否能被正确回答；商业项目才进一步查获客/付费/渠道。用户自己说需要是自用需求证据，不是商业市场证据。

落地途径按用户目标与资源选择，详见[落地途径](delivery-paths.md)。实现方式与发布/经营方式分开；先自用或原型再开源/商业化可以是合理顺序，不能把路线建议当部署、发布或付款授权。

投入意愿与工作量估计分开。用户给过边界就沿用；没给可提出轻量建议，不能伪造承诺，也不能据此无限研究。先缩首版范围、补最危险的未知，不牺牲保密、正确性或来源来赶进度。

已有充分证据可直接给复用或不做的结论，不强制原型。不执行未审第三方代码、不安装未批依赖；遇到权限栏杆完成其他安全分析后交付结论。

## 5. 需求变化时更新受影响链条

1. 区分需求变更与新证据：用户改变目标/场景/约束/优先级/验收才改需求版本；发现另一个候选不等于需求变了。
2. 在requirements变更表记录依据、受影响R编号和后续产物。
3. 对相关研究、decision、验证与verdict标“仍适用/需重评/已替代”，说明理由；旧评分不搬到新对象。
4. 保留无关证据，只重做受影响部分。既有确认不重问；尚未决定的意图只阻塞其依赖分支。
5. 需求未变但关键证据或假设被推翻，也要复核受影响方案和评分；不改需求版本，不继续沿用旧结论。
6. 发布当前结论前核对需求版本、证据与方案仍一致。脚本通过或文件存在不能证明这一点。

典型例子：主目标从一般归档改为专业过程追溯，会改变候选类别、验证和优先级；仅换一款软件名称但验收不变，不需要重新访谈所有需求。

## 来源与适配（公开资料核验于2026-10-31）

- [Design Council Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/)：理解问题、收敛定义、发展与交付，允许发现新信息后回访。没有把它解释成一次冻结后永不改变的瀑布。
- [GOV.UK Discovery](https://www.gov.uk/service-manual/agile-delivery/how-the-discovery-phase-works)：先理解问题和约束，可能得出不建设的结论；不照搬其政府审批和周数。
- [GOV.UK Alpha](https://www.gov.uk/service-manual/agile-delivery/how-the-alpha-phase-works)：只做足以检验最危险假设的原型；不把原型当生产交付。
- [Shape Up: Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03)及[Risks and Rabbit Holes](https://basecamp.com/shapeup/1.4-chapter-05)：区分愿意投入与估计工作量、明确不做的事、先处理会失控的未知；不套六周周期。
- [SVPG Four Big Risks](https://www.svpg.com/four-big-risks/)：四风险透镜；对自用/科研作上述口径适配，不替换本地维度/权重。

以上为机制归纳和署名，不搬第三方代码或整套框架。用户资料与本地项目内容不进入外部检索或评审材料。
